# Authentication redirect review

## Scope

The three original SAST findings were the authorization redirect, callback
return redirect, and end-session redirect in the API authentication router.
No scanner exclusions or suppression comments have been added.

## Remediation

- Browser-controlled return paths are canonicalized with the WHATWG URL parser
  against a fixed origin. External origins, protocol-relative paths, backslashes,
  control characters, invalid escaping, encoded leading slashes, and paths that
  normalize to protocol-relative URLs fall back to `/`. Both query parameters
  and cookies use this policy.
- Authentication callback and post-logout origins require an exact host from
  server-provisioned `REPLIT_DOMAINS`. Development also permits
  `REPLIT_DEV_DOMAIN`. Forwarded host headers alone do not establish trust, and
  forwarded protocol headers cannot downgrade HTTPS. Unknown hosts fail closed.
  Deployments/custom domains must be present in the provisioned domain list.
- Authorization and logout redirects must have the exact origin and pathname
  from the corresponding server-side OIDC discovery endpoint. HTTP endpoints,
  credentials, fragments, missing metadata, and endpoint mismatches are rejected.
  Query parameters generated by `openid-client` remain intact.
- The local redirect sink independently enforces a single leading slash and
  rejects backslashes/control characters. OIDC redirects are reconstructed
  from discovery metadata; the caller's `href` is never forwarded, even if
  an unexpected URL object has overridden it.

OIDC discovery is a trusted configuration boundary, not a browser-controlled
allowlist. The configured issuer and its discovered endpoints must remain
trusted. PKCE, state, nonce, and ID-token validation are unchanged.

## Ownership coverage review

The previous removal addressed an orphaned runner but did not restore the
missing integration coverage. The historical suite and cleanup utility existed
on other local history, not in this branch; that history also depended on
ownership implementation absent from the branch.

The restored runner is invoked by `pnpm --filter @workspace/api-server test`
(or `run test:integration`). It creates a new temporary PostgreSQL cluster with
a private Unix socket and pushes the current schema only into that empty
database. It does **not** accept an existing `DATABASE_URL` as the test target.
It stops its PostgreSQL server and removes its own temporary directory on test
failure or interruption. Cleanup-failure and interrupted-subprocess tests
exercise this behavior. No fixture-prefix SQL deletion can affect user data.
PostgreSQL `initdb` and `pg_ctl` must be on PATH; missing tooling fails explicitly,
with no fallback to the application database.

The tests create two users and real sessions, seed independent records, and
exercise authenticated list/read/update/delete APIs. Coverage includes
opportunities, competitors, meetings, feedback, signals, product-workspace
aggregation, conversations created through authenticated APIs, and disclosure
of legacy unassigned insights. Demo database tests now run on this same
disposable target. This is real runtime coverage, not the historical
source-text/regex assertions.

The ownership run currently has **4 passes and 11 failures** (including two
passing demo tests). Failures demonstrate cross-owner list/read/delete access,
cross-owner workspace aggregation, globally shared conversations, and legacy
insight disclosure. Opportunity list/access isolation passes.

The full historical validation/roadmap/document/AI ownership matrix has not
been restored here. Expanding that coverage and repairing the missing
application ownership implementation remain outstanding. Conversations and AI
insights lack persistent owner fields in the current schema; legacy records
cannot safely be assigned to users by guessing. The failing tests are
intentional evidence of unresolved application behavior, not suppressed or
skipped checks. This branch should not be described as fully security-validated.
